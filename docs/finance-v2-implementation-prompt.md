## 1. Архитектура

**Клиент:** существующие HTML, CSS и ES-модули, текущие темы и компоненты. **Локальные данные:** IndexedDB. **Серверные данные:** Google Cloud Firestore. **Вход:** Firebase Authentication, сначала Google. **Разделение пользователей:** путь по Firebase UID. **Будущий хостинг:** GitHub Pages.

Firestore и Auth использовать через официальный Web SDK. Обязательного собственного Node-сервера или Cloud Functions в первом ядре нет. Firebase работает на Spark; подключение платёжного аккаунта не входит в задачу. Первые проверки — локальный эмулятор с вымышленными пользователями и данными.

```text
finance/
  core/
    money.js              Денежные единицы, валюты, точный парсинг
    entities.js           Формы сущностей и проверка полей/ссылок
    commands.js           Бизнес-команды и их преобразование в изменения
    ledger.js             Влияние операций на счета, доходы и расходы
    budgets.js            Расход бюджета и остаток лимита
    goals.js              Резервы, прогресс целей и недостаток обеспечения
    selectors.js          Выборки и аналитика, адаптер прежних графиков
  local/
    db.js                 Открытие IndexedDB, stores, индексы и версии
    migrations.js         Локальные миграции без потери очереди
```

Это границы ответственности, а не требование сразу создавать пустые файлы. `core` не импортирует DOM, IndexedDB или Firebase. UI не вызывает Firestore и не пишет IndexedDB самостоятельно. Адаптер данных можно заменить без изменения финансовых правил. Появление SDK допускает небольшую сборку статического приложения; менять UI-фреймворк не требуется.

Контракт репозитория: `open(identity)`, `query(selector)`, `subscribe(listener)`, `dispatch(command)`, `exportRecovery()`. `dispatch` возвращает локальное подтверждение и `opId` только после завершения IndexedDB-транзакции. Отдельный `SyncEngine` предоставляет `start()`, `stop()`, `syncNow()` и наблюдаемый статус; подключение собирается в `controller.js`.

## 2. Правила модели

Сущности: `accounts`, `categories`, `sources`, `transactions`, `legacyIncomeMonths`, `budgets`, `goals`, `goalAllocations`. У синхронизируемой сущности — стабильный ID, серверная версия, времена создания/изменения, отметка удаления и `lastOpId`.

- Деньги — целые минимальные единицы. Начальные валюты RUB, USD, EUR. Разные валюты не складывать; курсы и полный поиск валют отложить.
- Расход обязательно связан со счётом и категорией. «Без категории» — стабильная системная категория. Для дохода есть источник, по умолчанию «Другие доходы».
- Операции: доход, расход, перевод, возврат расхода, начальный остаток и корректировка. Месячные суммы старого приложения хранятся отдельно.
- Перевод — один документ с двумя счетами и двумя суммами. Сначала только одинаковая валюта с равными суммами. Перевод не считается доходом или расходом.
- Остатки вычисляются из движений; поля «текущий баланс» как независимо редактируемого источника истины нет. Расходы не блокируются из-за отрицательного расчётного остатка.
- Бюджет — месячный лимит по категории/валюте либо общий по валюте. Использование = расходы минус возвраты. Переноса лимита между месяцами пока нет.
- Накопление — цель и резервы денег на счетах. Резерв не является расходом или переводом. Недостаток обеспечения показывается явно.
- Архивирование справочника сохраняет прошлые операции. Удаление операции синхронизируется как tombstone; не удалять запись физически на клиенте.
- Даты операций хранятся как календарные строки, без сдвига через UTC. Серверные временные метки не заменяют дату покупки.

Старым графикам передавать адаптированную месячную проекцию по источникам и выбранной валюте. Не менять формулы прежних графиков на каждом этапе. Для новых операций группировать платежи в месяцы; исторический `0` сохранять как наблюдение, а отсутствие записи — как отсутствие. История v1 и новые платежи не должны перекрываться по периоду учёта.

## 3. Сохранение и синхронизация

Путь любого изменения: **форма → бизнес-команда → транзакция IndexedDB (проекция + очередь) → синхронизация → транзакция Firestore → получение подтверждённого результата**.

В IndexedDB отдельно хранить подтверждённые сущности, проекцию, очередь, конфликты, метаданные и staging. Идентичность локальной базы включает проект Firebase, UID и книгу. Даже онлайн форма сначала сохраняет в локальную очередь.

У команды есть `opId`, эпоха книги, ожидаемые версии, изменения и hash неизменного запроса. ID создаётся до отправки. Потерянный ответ повторяется с тем же `opId`; результат определяется по серверной квитанции. Новые правки той же записи ждут подтверждения предшественника и сохраняются отдельными локальными намерениями.

На сервере данные находятся в `users/{uid}/books/{bookId}` и коллекциях активной эпохи: `entities`, `commits`, `receipts`. Одна транзакция проверяет версии, изменяет сущность, добавляет журнал и квитанцию, увеличивает последовательность книги. В первом прототипе одна бизнес-сущность на команду. Взаимосвязанные группы добавлять после проверки правил.

Чтение изменений идёт по серверной последовательности. Новые данные, собственное подтверждение, пересчёт проекции и cursor применяются локально вместе. Курсор нельзя перепрыгивать до номера собственного сохранения, пропуская чужие изменения. Квитанция не удаляет очередь до получения подтверждённого результата.

Конкурирующие изменения одной записи не перезаписывать автоматически: сохранять исходный, локальный и серверный варианты. Пользователь выбирает результат, после чего создаётся новая команда с актуальной базовой версией. Независимые расходы разных устройств сохраняются оба.

При смене пользователя останавливать старую синхронизацию, изолировать локальные базы и игнорировать поздние ответы. При истечении входа сохранять очередь. Восстановление резервной копии меняет эпоху и останавливает старые команды до сверки.

Не включать постоянный офлайн-кэш Firestore поверх собственной очереди: SDK использует память. Фоновая синхронизация при закрытой PWA необязательна; обязательна отправка при следующем запуске/возврате и доступной сети. Service worker кэширует оболочку и ресурсы, не финансовые ответы.

Подробные состояния, согласованный снимок, повторы, вкладки и проверочные сценарии описаны в `docs/finance-v2-sync.md`; соблюдать их при реализации, не заменять общей перезаписью коллекции.

## 4. Этапы и результаты

1. **Ядро и локальный репозиторий.** Деньги, счета, категории, расход, IndexedDB, очередь и проекция. Результат: синтетический расход и категория переживают перезапуск, сохранение атомарно. Не начинать с большой перестройки экранов.
2. **Изоляция и синхронизация в эмуляторе.** Auth, Firestore-адаптер, правила, квитанции, журнал, конфликты. Результат: два пользователя изолированы; два устройства сходятся без дублей и потерь после разрыва связи.
3. **Первый полноценный пользовательский сценарий.** Форма и список расходов, создание категорий, выбор счёта, офлайн-запуск и статусы отправки. Категории: название, цвет и библиотека минимум из 150 локальных иконок Lucide с русским поиском; хранить стабильный `iconId`, не произвольный SVG.
4. **Денежные движения и старая история.** Новые доходы, переводы, начальные остатки, возвраты и миграция v1. Результат: балансы и месячные отчёты сходятся, переводы исключены из доходов/расходов, повторный импорт не создаёт дублей.
5. **Бюджеты и накопления.** Лимиты, цели, резервы и связанные представления. Результат: корректный остаток бюджета и прогресс целей без смешения валют или двойного учёта денег.
6. **Подготовка к реальным данным.** Полный экспорт/восстановление, проверка PWA на целевых устройствах, план независимых резервных копий и контрольный импорт. Реальное облако, миграция и публикация выполняются только по отдельному запросу.

Переходить к следующему этапу после проверки результата текущего. При отсутствии облачного проекта продолжать работу в эмуляторе; не подключать вместо него рабочую Google Таблицу. Рутинные решения внутри архитектуры принимать самостоятельно. Изменение самой архитектуры объяснять конкретным обнаруженным препятствием.

## 5. Обязательные ограничения и проверка

- Существующая история и исходный проект неприкосновенны. `.local/` не читать для поиска рабочих токенов, не копировать и не коммитить.
- Не публиковать сайт, репозиторий, правила Firebase или Apps Script без отдельного запроса. Не создавать новый платный сервис.
- Не использовать browser use / computer use без явного разрешения пользователя. Для недоступных без них проверок подготовить точные ручные шаги и честно указать, что ещё не проверено.
- До записи реальных данных сделать настройку личного устройства, поведение выхода с очередью и проверенный файл восстановления.
- Для модели проверить деньги, даты, переводы, возвраты, бюджеты и резервы. Для синхронизации — потерянный ответ, конкуренцию, удаления, смену пользователя/эпохи, миграции и сбои IndexedDB. Для Firestore — попытки чтения чужих данных и записи в обход журнала.
- Не выдавать кэш формы за офлайн-режим, а отправку без квитанций — за надёжную синхронизацию. Не считать эмулятор проверкой реального мобильного service worker.

Начать с этапа 1. В отчётах кратко указывать реализованный результат, выполненные проверки и остающиеся ограничения; не возвращаться к общему выбору базы данных и декоративному редизайну.
