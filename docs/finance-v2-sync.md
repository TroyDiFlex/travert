# finance-v2: IndexedDB и синхронизация

Контракт от 2026-09-14. Локальная очередь и провайдер-независимый цикл синхронизации уже реализованы и проверены на детерминированном имитаторе, включая потерянный ответ, зависимости и конфликт трёх версий. Серверный адаптер не выбран: сервисы, требующие карту или платёжный профиль, исключены. Контекст, модель денег и этапы — в [основном документе](finance-v2.md).

## Гарантии и границы

- Одно нажатие «Сохранить» создаёт одну логическую команду. Повтор отправки использует тот же `opId` и не применяет её повторно.
- Подтверждение «Сохранено на устройстве» появляется только после завершения транзакции IndexedDB, включающей данные и очередь.
- Подтверждение сервера означает атомарную фиксацию сущностей, журнала, номера последовательности и квитанции.
- Изменения разных записей согласуются независимо. Конкурирующие правки одной записи требуют решения пользователя; часы устройств не выбирают победителя.
- Перевод между счетами — одна сущность, поэтому половина перевода не может синхронизироваться отдельно.
- Полная офлайн-работа предполагает ранее загруженное приложение и книгу на доверенном устройстве. Первый вход и первое получение данных требуют сети.

Собственная очередь в IndexedDB остаётся единственным постоянным клиентским хранилищем финансов. Будущий сетевой SDK не должен включать второй постоянный офлайн-кэш или самостоятельно разрешать конфликты правилом «последняя запись победила». Сетевые транзакции могут повторяться, поэтому их callback не меняет IndexedDB, DOM или состояние очереди.

## Локальная база

Имя базы включает пространство будущего сервера, ID пользователя и ID книги: `travsen-finance:<backendId>:<uid>:<bookId>`. До подключения сервера используются стабильные локальные значения. Локальный `dbVersion`, версия финансовой схемы, версия протокола и серверная `activeEpoch` имеют разные назначения. `activeEpoch` меняется при восстановлении данных, а не при каждом выпуске интерфейса.

| Object store | Содержимое |
| :--- | :--- |
| `serverEntities` | Последние подтверждённые сущности и tombstone по ключу `[entityType, id]`. |
| `viewEntities` | Материализованная проекция подтверждённого состояния и незавершённых локальных команд. Восстанавливается из базы и очереди. |
| `outbox` | `opId`, локальный порядок, команда, исходное состояние, зависимости, замороженный запрос и состояние отправки. |
| `conflicts` | Исходная, локальная и серверная версии; причина, затронутые операции и решение. |
| `meta` | Идентичность книги, эпоха, непрерывно полученный cursor, версии схем, лидер отправки, времена синхронизации. |
| `staging` | Изолированная область начальной загрузки, восстановления или миграции до полной проверки. |

Индексы проекции: тип и дата; счёт и дата; категория и месяц; источник и месяц. Для переводов индексируются оба счёта, например через `accountIds` и подходящий вспомогательный индекс. Очередь индексируется по состоянию и локальному порядку. Уникальные ключи месячных итогов, бюджетов и резервов детерминированы внутри книги; повторяемые реальные расходы имеют случайные UUID.

Сначала подготовить и проверить команду в памяти, затем одной короткой `readwrite`-транзакцией перечитать актуальную локальную версию, обновить проекцию и записать очередь. При конкуренции вкладок повторить построение от нового состояния. Не выполнять сеть или долгие вычисления внутри транзакции. Ждать `transaction.complete`, а не только успеха отдельного запроса. [Жизненный цикл IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Using_IndexedDB).

Ошибка записи или переполнение хранилища оставляет форму незавершённой: нельзя показывать успешное сохранение и держать единственную копию в памяти. Запросить `navigator.storage.persist()` после настройки личного устройства, обработать отказ. Это снижает риск автоматической очистки, но не заменяет экспорт и серверную копию. [Persistent storage](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/persist).

Изменение схемы обрабатывает `blocked` и `versionchange`: старые вкладки закрывают соединение с базой. Очередь преобразуется вместе с данными; несовместимость не исправляется удалением базы. Долгую миграцию делать через staging с проверкой и переключением активной генерации. Старый клиент при новой неподдерживаемой схеме открывает экран обновления без записи.

## Контракт команды

Пример условный, с вымышленными данными:

```json
{
  "protocolVersion": 2,
  "bookId": "demo-book",
  "epoch": "demo-epoch",
  "deviceId": "demo-device",
  "opId": "demo-op-uuid",
  "changes": [{
    "entityType": "transactions",
    "id": "demo-transaction-uuid",
    "expectedVersion": 0,
    "action": "create",
    "value": {
      "kind": "expense",
      "date": "2026-10-01",
      "accountId": "demo-cash-rub",
      "categoryId": "demo-food",
      "amountMinor": 12500,
      "currency": "RUB",
      "note": "Пример"
    }
  }]
}
```

`expectedVersion = 0` допустима только при отсутствии ID, включая отсутствие tombstone. Для изменения, удаления или восстановления нужна точная текущая версия. Внешний `uid` определяется проверенной сервером авторизацией и путём книги; переданное в теле имя пользователя не даёт полномочий.

Запрос нормализуется и получает `payloadHash` до первой отправки. Исключить из hash токены и счётчик повторов; включить книгу, эпоху, изменения и ожидаемые версии. После первой отправки `opId`, payload и hash неизменны, даже если ответ потерялся. SHA-256 здесь связывает квитанцию с запросом, а не заменяет авторизацию.

Последующие локальные правки той же сущности получают зависимости `dependsOn`. Они видимы в проекции, но их сетевой запрос фиксируется только после подтверждения предшественника. Зависимость также нужна расходу от ещё не отправленного создания счёта или категории. При конфликте предшественника вся зависимая цепочка сохраняется и останавливается.

В первой реализации одна бизнес-сущность на команду; перевод укладывается в этот предел. Группы из нескольких сущностей вводить отдельно для согласованных возвратов и резервов после проверки лимитов правил. Транспортная пачка не должна создавать иллюзию общей атомарности независимых команд.

## Сервер и атомарное подтверждение

Предлагаемая структура:

```text
users/{uid}/books/{bookId}
  activeEpoch, schemaVersion, minProtocolVersion, headSeq
  epochs/{epoch}/entities/{entityKey}
  epochs/{epoch}/commits/{opId}
  epochs/{epoch}/receipts/{opId}
```

`entityKey` кодирует тип и ID. `commits` содержит последовательность `seq`, `opId`, серверное время и полные новые версии изменённых сущностей, включая удаления. `receipts` — неизменяемые квитанции: hash запроса, `seq`, ID и версии результатов. Число `headSeq` относится к одной книге; общего счётчика всех пользователей нет.

В одной серверной транзакции:

1. Прочитать метаданные книги и квитанцию для `opId`. При смене эпохи остановить старую очередь. Если квитанция уже есть и hash совпадает — вернуть её без записи. Иной hash того же `opId` означает ошибку протокола.
2. Прочитать изменяемые сущности и нужные ссылки. Проверить ожидаемые версии, типы, валюты, доступность счетов/категорий и финансовые инварианты. Все чтения выполнить до записей.
3. Вычислить новые версии и `seq = headSeq + 1`. Атомарно записать сущности, commit, receipt и новое значение метаданных. Времена присваиваются сервером.
4. Вернуть квитанцию после завершения транзакции. Callback не меняет IndexedDB, DOM и состояние очереди: SDK может повторить его при конкуренции.

Минимальная запись одного расхода — ориентировочно четыре записи документов: сущность, commit, receipt и метаданные книги. Это собственная оценка схемы, а не тариф «одна операция = одна запись». Чтения, ссылки, правила, повторные попытки и дополнительные сущности потребляют квоту отдельно.

Сервер должен проверять UID в пути, типы полей, диапазоны денег, ссылки внутри книги, текущую эпоху и рост версии. Изменение сущности разрешается только вместе с соответствующим commit/receipt и обновлением последовательности; содержимое commit должно соответствовать записанным сущностям. Квитанции и подтверждённые commit нельзя переписать клиентом. Физические удаления клиентом запрещены — используются tombstone.

Кандидат сервера принимается только после локальной проверки всех путей обхода журнала и ограничений его транзакций. Если необходимая группа не укладывается в проверяемый контракт, нужно сузить группу или пересмотреть серверную часть; нельзя отключать изоляцию или контроль версий ради работоспособности.

Все будущие администраторские импорты, восстановление и очистка также обязаны соблюдать протокол. Ручное редактирование документов в консоли обходит часть клиентских гарантий и не является поддерживаемым способом изменения финансов.

## Цикл согласования

1. Выбрать текущую идентичность, эпоху и лидера отправки. Получить новые изменения после локального cursor; чтения должны быть подтверждены сервером, а не возвращены из кэша SDK.
2. Одной транзакцией IndexedDB применить целую последовательную страницу, обновить `serverEntities`, сверить собственные `opId`, пересчитать проекцию и продвинуть cursor. Курсор не продвигается через пропуск.
3. Отправить готовую команду с учётом зависимостей. При успехе пометить её `committed-awaiting-pull`, сохранив квитанцию.
4. Получить журнал до `receipt.seq`. В той же локальной транзакции, которая включает подтверждённый результат, убрать соответствующее намерение из проекции/очереди и разблокировать зависимости. Это исключает удвоение эффекта операции.
5. Повторять, пока есть готовые команды. После входа, `online`, возврата приложения на экран и ручной синхронизации запускать этот же цикл. Пока приложение видно, можно слушать только изменение метаданных книги и затем дочитывать журнал.

`headSeq` из ответа на отправку не заменяет cursor: между ними могут быть чужие изменения, которые устройство ещё не получило. Повторные страницы и уже виденные версии безопасно пропускаются. Поздний ответ старого пользователя, поколения базы или эпохи игнорируется.

Таблицу состояний очереди проектировать явно:

| Состояние | Действие |
| :--- | :--- |
| `pending` | Готово к отправке после зависимостей. |
| `sending` | Запрос заморожен; параллельная отправка ограничена лидером. |
| `unknown` | Ответ потерян: повторить тот же запрос и найти квитанцию. |
| `committed-awaiting-pull` | Сервер подтвердил; получить данные до нужного `seq`. |
| `conflict` | Сохранить три версии и ожидать решения пользователя. |
| `blocked` | Нужны вход, обновление, доступная квота, исправление данных или решение зависимости. |

Сетевой сбой, временная недоступность и конкуренция используют ограниченные повторы с увеличением паузы и случайным разбросом. Пример: 2, 5, 15, 30, 60 секунд, затем ожидание события/ручного повтора. Исчерпание суточной квоты не опрашивать каждую минуту. `navigator.onLine` — сигнал попробовать, а не доказательство доступности сервера.

До первой отправки отмена команды возможна с пересчётом её зависимостей. После первой отправки нельзя просто удалить её из очереди: сначала установить результат по квитанции, затем при необходимости создать компенсирующее изменение.

## Конфликты

| Ситуация | Поведение |
| :--- | :--- |
| На двух устройствах созданы разные расходы | Оба сохраняются. |
| Одна сумма исправлена двумя устройствами | Вторая правка останавливается с исходной, локальной и серверной версиями. Автоматического выбора по времени нет. |
| Расход удалён на одном устройстве и исправлен на другом | Сохраняется конфликт с удалением; запись не воскресает автоматически. |
| Категория переименована, расход на неё добавлен | Ссылка по ID остаётся; сам расход не конфликтует с названием. |
| Счёт архивирован, пока другое устройство офлайн | Новую запись нужно подтвердить после выбора допустимого счёта либо восстановления счёта. Данные формы/очереди сохраняются. |
| Старое изменение против новой эпохи после восстановления | Требуется сверка или экспорт старой очереди, автоматической отправки нет. |

Решения: принять серверную версию; создать новую команду с локальным вариантом относительно актуальной серверной версии; вручную объединить. Перед «сохранить мой вариант» перечитать текущую версию, поскольку она могла измениться после открытия конфликта. Первоначальная квитанция и запрос не переписываются. Зависимые команды сохраняются до явного перебазирования или отмены.

## Первичная загрузка и длинный офлайн

Одна непоследовательная выгрузка страниц коллекции не считается согласованным снимком. Предлагаемый алгоритм без отдельного сервера:

1. С сервера прочитать эпоху и `headSeq = H0`.
2. Загрузить в staging все сущности этой эпохи страницами по стабильному ID, вместе с tombstone.
3. С сервера прочитать `H1` и эпоху повторно. Если эпоха поменялась — не активировать staging.
4. Последовательно применить commit из интервала `(H0, H1]`, учитывая версии. Они исправляют изменения, произошедшие во время постраничного чтения, включая появление новых ID за уже прочитанной страницей.
5. Проверить непрерывность журнала, структуру и ссылки. Атомарно активировать полученное состояние на `H1`, сохранив локальные команды отдельно и пересчитав проекцию.

Предпосылка: все изменения сущностей атомарно отражены в метаданных и журнале. Отсутствие этой гарантии делает алгоритм неверным. Во время отправки/снимка изменение `activeEpoch` требует остановки и повторной сверки.

Первый релиз не очищает журнал и квитанции автоматически; измеряет их объём. До исчерпания пространства вводится проверенная компактация: снимок, `minCursor` и квитанции без повторного применения операций. При старом cursor клиент получает требование полного снимка, а не пустой список изменений. Старые `opId` и ID удалённых сущностей нельзя молча забыть внутри той же эпохи.

При полном обновлении базы очередь не стирается. Подтверждённые ранее `opId` сверяются с квитанциями; остальные намерения перебазируются с проверкой исходных версий. JSON-экспорт очереди доступен до любой неподдерживаемой миграции.

## Service worker и вкладки

Service worker обслуживает только файлы приложения. Кэш версионируется и ограничен путём будущего GitHub Pages-проекта; навигация использует офлайн-оболочку только внутри этого пути. Финансовые ответы API, токены и чужие URL в Cache Storage не сохраняются. SDK, шрифты и иконки, необходимые для запуска, должны быть доступны из локального пакета.

Не принуждать вкладки немедленно переходить на новую версию worker во время сохранения. Обновление оболочки согласуется с поддерживаемой версией базы; не удалять старые кэши других приложений того же origin.

Один координатор отправки на локальную книгу: предпочтительно Web Locks, с резервной арендой в IndexedDB и обменом уведомлениями через BroadcastChannel. Просроченная аренда восстанавливается после закрытия вкладки. Даже при двух лидерах серверная квитанция обязана предотвратить дубликат; блокировка вкладок лишь снижает лишние запросы.

Background Sync не является обязательной частью первого релиза: он доступен не во всех распространённых браузерах. При закрытом приложении нельзя обещать фоновую отправку; гарантированный путь — следующий запуск/возврат и доступная сеть. Позднее фоновой отправке потребуется тот же координатор и корректное получение авторизации. [Background Synchronization API](https://developer.mozilla.org/en-US/docs/Web/API/Background_Synchronization_API).

Пользовательские статусы: «Сохранено на устройстве», «Ожидают отправки: N», «Синхронизировано», «Нужно войти», «Нужно решить конфликт». Отдельно хранить время последней подтверждённой синхронизации; обычный перерендер не обновляет его.

## Проверки перед реальными данными

| Проверка | Что должно сохраниться |
| :--- | :--- |
| Сбой между локальной записью и добавлением в очередь | Обе записи есть или обе отсутствуют. |
| Перезапуск после офлайн-расхода | Сумма, категория, счёт, очередь и статус. |
| Успешная серверная запись с потерянным ответом | Один расход и одна квитанция после повторов. |
| Сбой после получения квитанции до её локальной записи | Повтор находит прежнюю квитанцию. |
| Две вкладки и два устройства | Нет дублей; независимые изменения сходятся, конкурирующие видимы. |
| Поздняя pull-страница и новые локальные правки | Новые намерения не исчезают, версия не откатывается. |
| Сбой применения страницы | Данные и cursor откатываются вместе. |
| Перевод / возврат / удаление | Нет половины перевода, двойного расхода или случайного восстановления. |
| Смена пользователя, выход и истечение входа | Чужая база недоступна; старая очередь не уходит новому пользователю. |
| Запросы без Auth, с чужим UID или в обход журнала | Отказ серверных правил, проверенный в локальном тестовом окружении. |
| Часы устройства ушли вперёд или назад | Нет потери конфликтующих данных и нарушения server seq. |
| Новая схема, blocked-вкладка, нехватка места | Очередь сохранена; ложного подтверждения нет. |
| Изменения во время постраничного снимка | Итог соответствует `H1`, без пропусков и повторного эффекта. |
| Старая очередь после восстановления | Остановка по эпохе и возможность сверки/экспорта. |
| Исчерпана квота / недоступен Google | Локальная работа сохраняется; нет бесконечного активного опроса. |
| Нули, пустые месяцы и корзина v1 | Миграция сохраняет различия и сверяемые месячные суммы. |
| RUB, USD и EUR одновременно | Валюты не складываются без явного курса. |
| Резервная копия и восстановление в новую книгу | Совпадают все сущности, удаления, настройки и расчёты. |

Сначала чистые тесты модели и детерминированный имитатор серверного контракта, затем локальное тестовое окружение выбранного сервера. После этого проверить IndexedDB и service worker в реальных целевых браузерах и установленной мобильной PWA. Автоматическое управление браузером в этом проекте требует явного разрешения пользователя; без него такие сценарии выполняются вручную по проверочному списку.
